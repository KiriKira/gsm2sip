# gsm2sip 网关代码与现有计划审查

## 核查范围

通过 GitHub 插件读取了 KiriKira/gsm2sip 的 main，提交为 477b7e349891928dda7b87a9b55b72c52e7eab87。审查对象是此提交中的源码与原PLAN-selfhosted-gateway.md。报告仅记录审查时的代码现状；随后提交的是新计划，功能尚未实现。

## 结论

gsm2sip 已经有完整的单通话 SIP↔蜂窝桥接骨架，也有 SMS 广播接收、持久化队列、分片发送及状态回报。它能作为旧 root Android 网关的代码基础，但当前没有完成双 SIM 选卡：呼出蜂窝电话会落到 Android 系统默认线路，入站电话没有把线路身份带给服务器；短信虽能记录 subscriptionId 和 slot，却会在选择无效时回退到默认 SIM。以当前状态不能保证“从主机指定哪张卡就由哪张卡拨号或发短信”。

音频有设备适配代码和少数机型的实机记录，不代表任一已 root Android 都能双向通话。用户的旧手机型号、ROM 与双卡并发能力未知；要先按目标机型逐卡实测，再把它定为可支持硬件。现有计划的总体安全方向合理，但短信/状态/控制架构需改成三端协议 v1 的 HTTPS/WSS 数据面，并补上稳定 SIM 映射、蜂窝拨号选卡、DTMF 和更严格的持久化验收。

## 代码现状与影响

| 领域 | 源码证据 | 对计划的影响 |
|---|---|---|
| GSM 呼出选卡 | GsmCallManager.makeCall(context, destination) 以 telecom.placeCall(uri, Bundle()) 呼出，没有 EXTRA_PHONE_ACCOUNT_HANDLE；失败时还会启动不带 account 的 ACTION_CALL（GsmCallManager.kt，makeCall）。 | 双 SIM 呼出选卡未实现。须由已校验的 sim_id 找到当前 PhoneAccountHandle，并在拨号时显式传入；找不到或映射不一致要拒绝，不能交给 Android 默认线路。 |
| GSM 入站选卡 | GsmCallManager.onCallAdded() 只读取 Call.Details.handle 中的对端号码，没有读取/映射 Call.Details.accountHandle；CallOrchestrator.onIncomingGsmCall() 与 handleInboundFlow() 也不带 SIM 身份。 | 主叫号码不能区分同一网关的两张线路。计划需要求从实际 PhoneAccountHandle 解析 SIM，入站 SIP INVITE 带 sim_id、mapping_revision 和业务 call_id。 |
| 全局并发 | GsmCallManager 只有一个 activeCall；CallOrchestrator 只有一个 activeGsmCall、activeSipCall 与 bridgeState，并在非 IDLE 时拒绝新来电。 | 全设备最多一条桥接通话是当前真实限制。可以保留为 v1 限制，但要明确覆盖卡 1、卡 2、呼入、呼出、拨号中及振铃中状态，不能因第二张卡另建服务绕过。 |
| 入站短信识别 | SmsReceiver.onReceive() 收到 SMS_RECEIVED 后读 EXTRA_SUBSCRIPTION_INDEX / subscription，再用 SubscriptionManager 获取 slot、运营商和可读号码；即使订阅信息失败仍写入队列，并以 subId/slot 头转发（SmsReceiver.kt，onReceive/describeSim；GatewayService.kt，sendSmsOverSip）。 | 这是有用的观测信息，但不是稳定的 SIM 身份。无法确认线路时仍保留短信事件，标记 sim_id=null / unknown；主机不得显示“原卡回复”或“原卡回拨”。 |
| 出站短信选卡 | GatewayService.resolveSubscription() 接受 SIP MESSAGE 中的 subId 或 slot；slot 找不到 active subscription 时明确记录“using default”。SmsSender.smsManagerFor() 在 createForSubscriptionId 失败时回退到 base SmsManager，subId 无效时也直接用 base；app minSdk 26，但此 createForSubscriptionId 调用需要按 API 版本分支（GatewayService.kt，resolveSubscription；SmsSender.kt，smsManagerFor）。 | 这是误用另一张 SIM 的直接风险。生产发送命令改用经确认的 sim_id+mapping_revision 解析到当前 subId；API 31+ 使用 createForSubscriptionId，较旧系统走对应的 subscription-bound API；任何版本绑定失败均失败关闭，不能 catch 后用默认实例。 |
| 现有 SMS 队列边界 | SmsStore 用 SharedPreferences 写入，但超过 200 条会移除最旧项目；SmsOutbox.add() 只保留最后 200 条，prune()/remove() 会删除任务行，且 onSmsSendRequest() 只在当前 outbox 查重（SmsStore.kt，add；SmsOutbox.kt，add/prune/remove；GatewayService.kt，onSmsSendRequest）。 | 满队列可能丢未完成任务；终态数据清理后，重放同一个 message id 可能再发。把正文/回执保留期与幂等 tombstone 分开；保留已接受的 ID 与终态，至少覆盖服务端命令重放保留期。超容量需回压/告警，不能 takeLast 丢未完成项；modem 调用后不确定进入 unknown，不能自动重发。 |
| 短信确认语义 | 当前入站短信走 SIP MESSAGE；GatewayService.flushSmsQueue() 在 SIP 返回 200/202 后删本地队列。旧 README 说明 Asterisk chan_sip 在 dialplan 执行前就自动回 202。SmsSendReceiver 虽收到 part_index，但 onSent()/onDelivered() 每次回调都对 sentOk/deliveredOk 做 +1，没有以 message_id+part_index 去重。 | SIP/Asterisk 2xx 不证明服务端数据库已提交。生产改走 HTTPS 批量事件上传，服务端数据库提交后逐项返回 durable event_id，网关收到后再标记可清理。短信分片状态按索引 upsert；WSS 仅作唤醒通知。 |
| 短信命令通道 | SipClient 接受 SIP MESSAGE 并调用 GatewayService.onSmsSendRequest()，从 X-SMS-Sim-Sub / Slot 选卡并写出站队列。 | 旧 SIP MESSAGE 仅用于现有实现基线或迁移适配；v1 生产只能由 HTTPS command claim 执行，不能保留两条各自可发送的并行通道。 |
| SIP↔RTP DTMF | SipMessage 的 SDP 始终声明 payload 101 telephone-event/8000 和 fmtp 0-16；RtpSession 收包仅接受语音 codec payload，代码库没有电话事件解码，也没有 Call.playDtmfTone()/stopDtmfTone()（SipMessage.kt，buildSdp/SDP answer；RtpSession.kt，RTP receive/decode）。 | DTMF 没有桥到蜂窝网。计划要明确实现/协商 RFC4733 telephone-event 到 Telecom Call.playDtmfTone()/stopDtmfTone() 的桥接，并用真实 IVR/语音信箱在两张 SIM 上验收；只看到 SIP RTP 包不算通过。 |
| TLS 与中文短信 | TlsSipTransport.receive() 每次 socket read 先把 UTF-8 字节解码为 String；takeMessage() 再把 SIP Content-Length 字节数与 StringBuilder.length 比较（SipTransport.kt，receive/takeMessage）。 | 旧计划 P1.1 仍是实在的发布阻塞项；保留字节缓冲，按字节数取帧，最后才解码正文，并测试中文码点跨读边界及多消息合并。 |
| 默认安全模式 | MainActivity.openConfigView() 的 server 默认仍是 callagent.pro、use_stun 默认为 true、srtp_enabled 默认为 false；SRTP 帮助文字明说对端未协商时继续明文 RTP（MainActivity.kt，openConfigView）。GatewayService 的启动读取路径也仍有 callagent.pro 默认值（GatewayService.kt）。 | 旧计划 P0/P2 有必要，且目前尚未落地。新安装默认不连第三方；生产 SIP/TLS、证书和主机名验证、SDES-SRTP 必须成功，不允许静默降级。 |
| 音频硬件可行性 | RtpSession.initAudio() 依赖 VOICE_CALL / VOICE_DOWNLINK 等 AudioRecord source、CAPTURE_AUDIO_OUTPUT、AudioTrack；DeviceProfile 通过 SoC/HAL 选 mixer profile。Magisk 模块把 APK 安装成 priv-app、设置 appops，并隐藏 PermissionController。 | Root 解决权限门槛的一部分，不能绕过厂商 Audio HAL 路由。README 记录 Poco X3 NFC（SM6150/SM7150）与 Galaxy S4 Mini（MSM8960）live call 双向可用；Exynos S10e 明确不可用。README 也指出供应商固件而非芯片单独决定支持。目标机型未知，且仓库没有逐 SIM 的双 SIM 通话记录，必须作为先决实测。 |
| 系统副作用 | Magisk service.sh 会把 Magisk root policy 强制改为 allow、取消 Android 全局 SMS 发送限额并静默系统短信通知；GatewayService 还会尝试修改默认短信应用数据库的已读状态（service.sh；GatewayService.kt，markInboxRead）。 | 旧计划 P3.1–P3.3 的修正必须保留。尤其不要把全系统限额改到无限；限流应由服务端与网关各自按 SIM 实施。 |

## 现有 PLAN-selfhosted-gateway.md 审查

应保留的部分：仓库拆分为 rooted gateway / server / non-root primary client；移除 callagent.pro 默认值；TLS 字节帧修复；生产强制 TLS 与 SRTP；认证、拨号和短信限流；审查全局权限/Root policy 修改；硬件 profile 实测；端到端断网、重启、中文短信测试。它把音频硬件适配识别为最大风险是准确的。

需调整的部分：

1. Phase 4 写“Keep SIP MESSAGE for gateway <-> server initially”，并把 HTTPS status 放在 later。这需要随本次三端协议 v1 修订；改成 HTTPS JSON 是短信、状态、命令唯一生产数据通道，WSS 只通知，SIP MESSAGE 仅迁移/兼容测试且生产发送器关闭。
2. 所有作为路由依据的 X-SMS-Sim-Sub / Slot 例子，改为稳定服务端 sim_id 和网关 mapping_revision。Android subscriptionId、slot 和 PhoneAccountHandle 是本地当前映射值；校验通过的同卡映射可跨普通重启保持，不要错误地要求每次重启重新生成。换卡、映射变更或身份无法确认时需要更新 revision/本地确认，绝不默认回退。
3. 呼出流程补上从可信 server-generated X-GSM-Sim-Id 与 mapping_revision 到 Android PhoneAccountHandle 的链路；呼入流程识别来电 PhoneAccountHandle 并带出同一 sim_id。客户端自带的 X-* 头不作为授权依据，服务器负责校验 SIM 权限并剥除/覆盖不可信路由头。
4. Outbound SMS 的 202 不可以只对应“写入 SharedPreferences”。参照协议的网关命令账本，先原子写入 message_id、sim_id、mapping_revision 与 dispatching 状态，再调用指定 modem；在 modem 已被调用、回执缺失的崩溃窗口记 unknown，不重复发送。入站事件在 server durable ACK 前不能从网关删除。
5. Phase 6 主机 V1 提议用外部 Linphone；三端协议 v1 要求主机应用内集成成熟 SIP SDK，并通过 HTTPS 先建立 call-intent，再建立指定 SIP leg。应由服务端权威协议/主机计划统一裁定，不能沿用相互矛盾的双版本目标。
6. 增加 DTMF 缺口与双 SIM 分别验收；包括每张 SIM 的入站/出站、短信原卡回复、SIM 换槽/换卡、呼叫进行时另一卡短信/来电、实际运营商 DSDS 限制以及 RFC4733 IVR。不能把“Android 看见两张 active subscription”当作通过。
7. README 仍给出 Asterisk chan_sip 示例，而网关计划目标是 PJSIP。README、SIP 建联和 MESSAGE 遗留说明要随服务端权威的 PJSIP 协议更新，避免用户照旧文档部署旧栈。

## 建议实施次序

- M0：删第三方默认值；保持 gateway-only；固定引用服务端协议版本；确定目标手机和 ROM，先跑 check-device.sh。
- M1：实现 sim_id/mapping_revision 本地绑定与状态同步；Telecom 入站 accountHandle 识别、出站 PhoneAccountHandle 显式选卡；SmsManager 严格绑定；无效映射失败关闭。先在两张 SIM 上单测运营商状态、短信、拨号选路。
- M2：迁移 SMS/status/control 到 HTTPS 与 WSS 通知；添加 Room/SQLite 的 event journal、持久序号、command ledger、幂等 claim/ack、unknown 状态；移除生产执行的 SIP MESSAGE 双通道。
- M3：修 UTF-8 TLS byte framing、registration expiry、SIP digest/安全设置、SRTP 无降级、限流与更安全 Magisk permission/root 行为。
- M4：实现 RFC4733 与 Telecom DTMF 桥接；目标机每张卡验证完整双向通话音频、振铃/接听/取消/挂断、IVR；如果任一 SIM 音频不通，不能宣传双卡语音已支持。
- M5：三端公网验收：主机指定卡拨号与收发短信、incoming call 回到正确 SIM 标签、过期 mapping 拒绝、服务器/网关断网重启恢复、短信事件 durable ACK 后清理、modem 不确定状态不重复执行。
